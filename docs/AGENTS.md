# AGENTS.md

## Project: 01-nexcent-landing

Это учебный **референс-проект**: лендинг по макету Figma полностью реализует AI
в соответствии с правилами качественной вёрстки.

Пользователь получает не «чужой результат», а **эталон идеального лендинга**,
который можно изучать, разбирать, задавать по нему вопросы и использовать
как образец для собственных работ и будущих собеседований.

---

# 1. Цель проекта

Цель — показать, как выглядит профессионально сверстанный лендинг
и как он устроен «по правилам»:

- семантический HTML;
- читаемый, структурированный CSS;
- соответствие макету Figma;
- адаптивность;
- состояния интерактивных элементов;
- плавные переходы и умеренные анимации;
- accessibility;
- чистота и порядок в коде;
- грамотные смысловые коммиты.

Проект должен максимально соответствовать макету по:

- структуре;
- расположению элементов;
- размерам;
- отступам;
- типографике;
- цветам;
- изображениям;
- кнопкам;
- карточкам;
- адаптивности;
- интерактивным состояниям;
- анимациям.

# 2. Роль AI

AI выполняет проект целиком и по всем правилам, как исполнитель реального заказа.

AI должен:

- анализировать макет в Figma и брать точные значения оттуда;
- не придумывать собственный дизайн там, где макет даёт готовое решение;
- писать код сам, поясняя по ходу ключевые решения;
- после завершения каждого этапа проводить code review собственного кода.

---

# 3. Роль пользователя

Пользователь изучает референс-реализацию:

- разбирает код по секциям;
- задаёт вопросы: почему выбрано то или иное решение;
- сравнивает код и результат с макетом;
- сам выполняет смысловые коммиты с правильными названиями;
- понимает и может объяснить любое место в коде.

Коммиты делает пользователь, а не AI.

AI подсказывает название коммита и список файлов для staging.

# 6. Коммиты

Проект изучается в том числе на примере идеальной истории коммитов.

Идеальный коммит: правильное название, правильный набор файлов
и своевременность — не слишком редкий и не слишком частый.

Правила:

- коммиты делает пользователь;
- каждый коммит — один логический блок работы;
- названия — по Conventional Commits (`feat`, `fix`, `style`, `refactor`, `docs`, `chore`);
- формат: `тип(область): краткое описание в повелительном наклонении`;
- без точки в конце, кратко (описание порядка 50 символов);
- в staging попадают только файлы, относящиеся к текущему коммиту;
- файлы, не относящиеся к коммиту, остаются untracked или не стейджатся.

AI перед каждым коммитом подсказывает:

- рекомендуемое название;
- точный список файлов для staging.

Критерии готовности коммита (все три обязательны):

- завершён логический блок (этап из раздела 5 или целая секция страницы);
- блок перед коммитом сверен с Figma;
- код самодостаточен — без незакрытых полуэтапов.

Своевременность:

- коммит создаётся, когда закрыт логический блок работы;
- не после каждой правки и не накоплением нескольких этапов;
- частота определяется завершённым результатом, а не временем.

Тип коммита отражает реальный эффект:

- `chore` — изменения без влияния на поведение страницы (структура, ассеты, чистка);
- `feat` — новый видимый результат (секция страницы, layout, адаптив, анимации);
- `style` — оформление без изменения логики базовых стилей;
- `docs` — документация.

Ориентировочная карта коммитов проекта:

1. `chore: init project structure`
2. `chore: add fonts and images`
3. `style: add base styles and variables`
4. `feat: add header section`
5. `feat: add hero section`
6. `feat: add clients section`
7. `feat: add community section`
8. `feat: add unlock section`
9. `feat: add achievements section`
10. `feat: add calender section`
11. `feat: add customers section`
12. `feat: add community updates section`
13. `feat: add cta and footer sections`
14. `feat: add responsive layout`
15. `style: add states and transitions`
16. `feat: add animations`
17. `docs: add README`

Карта ориентировочная: границы коммитов могут уточняться по ходу (дробиться
или объединяться), но каждый коммит сохраняет целостность логического блока.

# 8. HTML

Использовать семантический HTML.

По возможности использовать:

- header;
- nav;
- main;
- section;
- article;
- footer;
- ul / ol;
- button;
- a;
- form;
- label;
- input.

Заголовки должны иметь логичную иерархию
(один `h1`, ниже `h2`, затем `h3` и так далее).

HTML должен оставаться понятным даже при отключённом CSS.

Не использовать `<div>` для всего подряд,
если существует подходящий семантический HTML-элемент.

---

# 9. CSS

CSS должен быть:

- понятным;
- структурированным;
- читаемым;
- предсказуемым;
- без ненужного дублирования.

Сначала строится основа, затем визуальная полировка.

Для общих значений использовать CSS-переменные в `:root`
(цвета, шрифты, размеры, отступы).

Не решать каждую проблему большим количеством
абсолютного позиционирования.

Предпочитать:

- normal flow;
- Flexbox;
- Grid;

а absolute positioning использовать только тогда,
когда оно действительно оправдано дизайном.

---

# 10. Layout

При выборе способа построения layout использовать принцип:

Flexbox:

- header;
- навигация;
- горизонтальные группы;
- кнопки;
- выравнивание элементов;
- небольшие группы элементов.

Grid:

- сетки карточек;
- многоколоночные секции;
- статистика;
- колонки футера;
- сложные двумерные layouts.

Normal flow:

- обычный вертикальный поток;
- текстовые блоки;
- последовательные секции страницы.

Не использовать Grid или Flexbox только ради технологии,
если обычный flow решает задачу проще.

# 11. Адаптивность

Не ограничиваться только одним breakpoint.

Необходимо проверить:

- desktop;
- tablet;
- mobile;
- промежуточные размеры.

Особое внимание:

- отсутствие горизонтального скролла;
- размеры текста;
- переносы текста;
- размеры изображений;
- ширина контейнеров;
- расположение колонок;
- кнопки;
- навигация;
- карточки;
- отступы.

Если desktop и mobile версии Figma отличаются,
адаптив должен отражать эти изменения.

Для мобильной навигации использовать чистый CSS-гамбургер
(checkbox + label) без JavaScript.

---

# 12. Состояния элементов

Для интерактивных элементов реализовать:

- `:hover`;
- `:focus`;
- `:focus-visible`;
- `:active`;
- `:disabled` (где уместно).

Особенно важно не убирать видимый focus без альтернативы.

Состояния должны быть логичными и визуально согласованными
с дизайном проекта (State guide в макете).

---

# 13. Transitions

Для интерактивных элементов использовать плавные переходы,
если это улучшает взаимодействие.

Например:

- color;
- background-color;
- border-color;
- opacity;
- transform;
- box-shadow.

Не использовать transition для каждого свойства без необходимости.

---

# 14. Animations

Анимации должны быть умеренными.

Приоритет:

1. правильная структура;
2. соответствие макету;
3. адаптивность;
4. интерактивность;
5. accessibility;
6. только после этого дополнительные анимации.

Не превращать проект в демонстрацию CSS-анимаций.

Если анимация ухудшает восприятие страницы,
её лучше упростить или убрать.

Учитывать `prefers-reduced-motion`.

---

# 15. Accessibility

Проверять:

- семантическую HTML-разметку;
- alt у изображений;
- правильное использование button и a;
- keyboard navigation;
- focus-visible;
- контраст;
- структуру заголовков;
- доступность интерактивных элементов;
- label для form controls, если формы присутствуют;
- skip-link для перехода к основному контенту.

Не использовать только цвет для передачи важной информации.
