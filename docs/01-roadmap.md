🧩 Универсальный алгоритм разработки фронтенд-проекта

Главная идея:

Не начинать сразу писать код. Сначала понять задачу и макет, затем спроектировать структуру, потом реализовать, проверить и только после этого полировать.

Общая последовательность:

Макет → Анализ → Подготовка → HTML → Базовый CSS → Layout → Стилизация → Адаптив → Состояния → Анимации → Accessibility → Проверка → Полировка → Финал

1. 🔎 Изучить дизайн / макет

Перед написанием кода внимательно изучить макет.

Для этого репозитория: локальные экспорты макета лежат в
`docs/reference-images/` (PNG scale 2): общий вид — `full/landing-page.png`,
секции — `sections/`, палитра/кнопки/типографика/тени — `style-guide/`,
упрощённая версия — `mobile/mobile.png`.

Нужно понять:

какие страницы существуют;
какие секции есть на странице;
порядок секций;
размеры и пропорции;
цвета;
типографику;
отступы;
изображения;
иконки;
кнопки;
формы;
карточки;
повторяющиеся элементы;
desktop-версию;
mobile-версию.
Главное правило

Не начинать с:

«Так, сейчас сделаю <header>».

Сначала нужно получить целостное представление о странице.

2. 🧠 Декомпозировать макет

Разбить страницу на логические блоки.

Например:

Page
│
├── Header
│
├── Hero
│
├── Clients
│
├── Community
│   ├── Card
│   ├── Card
│   └── Card
│
├── Content section
│
├── Statistics
│
├── Blog / Cards
│
├── CTA
│
└── Footer

На этом этапе нужно определить:

что является самостоятельной секцией;
какие элементы повторяются;
какие элементы можно сделать переиспользуемыми;
где нужен Flexbox;
где Grid;
где обычный flow;
какие элементы являются контейнерами.

Это уже начало архитектурного мышления.

3. 📦 Подготовить assets

До активной вёрстки собрать всё необходимое:

изображения;
SVG;
иконки;
логотип;
шрифты;
favicon;
другие необходимые ресурсы.

Организовать их нормально.

Например:

nexcent-landing/
├── index.html
├── style.css
└── images/
    ├── logo.svg
    ├── hero.png
    ├── icon-1.svg
    └── ...

Не стоит в процессе разработки постоянно искать:

«А где же эта картинка из Figma?»

Лучше подготовить всё заранее.

4. 🏗️ Создать HTML-скелет

Сначала сделать структуру, а не пытаться сразу добиться идеального внешнего вида.

Например:

<header>
    ...
</header>

<main>
    <section>
        ...
    </section>

    <section>
        ...
    </section>

    <section>
        ...
    </section>
</main>

<footer>
    ...
</footer>

На этом этапе:

семантический HTML;
правильная иерархия заголовков;
header;
nav;
main;
section;
article;
footer;
списки;
ссылки;
кнопки;
формы.
Цель

Если отключить CSS, HTML всё равно должен иметь понятную структуру.

5. 🎨 Создать базовый CSS-фундамент

Теперь задаём основу проекта.

Например:

box-sizing;
body;
базовый font-family;
базовые размеры;
цвета;
background;
ссылки;
кнопки;
изображения;
контейнер;
общие переменные.

Например:

:root {
    --color-primary: ...;
    --color-text: ...;
    --color-background: ...;
}

Также здесь можно определить:

максимальную ширину контента;
общие horizontal padding;
базовую систему отступов.
6. 📐 Построить Layout

Теперь начинается непосредственно построение геометрии страницы.

Основные инструменты:

Flexbox

Для:

header;
навигации;
горизонтальных групп;
кнопок;
карточек;
выравнивания элементов.
Grid

Для:

сложных сеток;
карточек;
колонок;
статистики;
элементов, которые действительно образуют двумерную структуру.
Normal flow

Не нужно превращать всё в Flexbox.

Если элементы нормально располагаются обычным потоком — оставляем обычный flow.

Главная задача этапа

Получить правильную геометрию:

ширина
↓
колонки
↓
выравнивание
↓
отступы
↓
позиционирование
7. 🎯 Стилизация под Figma

Теперь постепенно приближаем результат к дизайну.

Работаем с:

цветами;
шрифтами;
font-size;
font-weight;
line-height;
letter-spacing;
border-radius;
shadows;
backgrounds;
borders;
spacing;
размерами изображений;
кнопками;
карточками.

Здесь уже начинается настоящее сравнение:

Figma ↔ браузер

И исправление расхождений.

8. 📱 Сделать адаптив

Очень важный этап.

Не просто:

«Поставлю один media query на 768px».

Нужно посмотреть, как именно макет меняется.

Например:

Desktop:

[Logo] [Nav] [Button]

Mobile:

[Logo]              [Menu]

Или:

Desktop:

[Image] [Text]

Mobile:

[Text]
[Image]

Проверяем:

desktop;
tablet;
mobile;
промежуточные размеры.

И главное:

Не только те два размера, которые есть в Figma.

Страница должна нормально работать и между ними.

9. 🖱️ Реализовать состояния

Очень важный пункт, который часто забывают.

Для интерактивных элементов проверить:

Hover
:hover
Focus
:focus

или лучше:

:focus-visible
Active
:active
Disabled
:disabled

Если состояние предусмотрено дизайном — повторить его.

Если в дизайне состояние не показано, всё равно подумать:

«Что произойдёт, когда пользователь наведёт мышь / нажмёт Tab / нажмёт кнопку?»

10. ✨ Добавить transitions

Не делать интерфейс «дерганым».

Например:

transition:
    background-color 0.2s ease,
    color 0.2s ease,
    transform 0.2s ease;

Плавно анимировать:

цвет;
background;
border;
opacity;
transform;
shadow.

Но не анимировать всё подряд.

11. 🎬 Добавить умеренные анимации

После того как всё работает, можно добавить:

появление элементов;
небольшие движения;
hover-анимации;
появление при загрузке;
scroll-анимации, если они действительно подходят.

Главный принцип:

Сначала функциональность и точность, потом animation.

Не наоборот.

12. ♿ Проверить Accessibility

Теперь отдельно пройтись по доступности.

Проверить:

семантический HTML;
alt у изображений;
правильные кнопки и ссылки;
keyboard navigation;
focus-visible;
читаемость текста;
контраст;
правильную структуру заголовков;
формы;
label;
состояния элементов.

Попробовать пройти страницу только клавиатурой.

Например:

Tab
Tab
Tab
Enter
Tab
...

И посмотреть:

Понятно ли, где я нахожусь?

13. 🧪 Проверить проект

Теперь тестируем.

Разные разрешения

Например:

1920
1440
1280
1024
768
480
375
320

Не обязательно каждый раз проверять все эти значения, но нужно посмотреть несколько разных размеров.

Проверяем:
нет ли горизонтального scroll;
не ломается ли layout;
не вылезает ли текст;
не слишком ли маленькие кнопки;
не ломаются ли изображения;
работает ли меню;
работают ли формы;
нет ли неожиданных наложений.
14. 🌐 Проверить кроссбраузерность

Минимально проверить основные браузеры:

Chrome;
Firefox;
Edge;
Safari — если будет возможность.

Не обязательно делать огромный QA-процесс для каждого учебного проекта.

Но нужно понимать:

CSS, который работает у меня в Chrome, ещё не автоматически означает идеальную работу везде.

15. 🔬 Полировка

Теперь начинается последний проход.

Сравниваем:

Figma
   ↕
Browser

И исправляем мелочи:

2px здесь;
4px там;
line-height;
размеры;
положение иконки;
border-radius;
shadow;
расстояние между элементами;
размеры контейнеров.

Но здесь важно не превратить это в бесконечное:

«Ещё один пиксель... ещё один...»

Нужно понимать, какие различия действительно важны.

16. 🧹 Рефакторинг и очистка

После того как проект работает:

Проверить:

нет ли дублирования CSS;
нет ли ненужных стилей;
понятные ли названия классов;
нет ли мёртвого кода;
логичная ли структура;
нормально ли организованы assets;
можно ли упростить некоторые решения.

То есть:

Сначала заставили работать → потом сделали код нормальным.

17. 📝 Git + README

После завершения привести проект в нормальный вид.

Git у тебя сейчас будет через Source Control в VS Code, что абсолютно нормально.

Для этого проекта можно делать commits по мере работы:

Initial project setup
Build page structure
Add header and hero
Build content sections
Add responsive layout
Add interactive states
Add animations
Improve accessibility
Final polish

А позже, когда дойдём до полноценного Git-этапа, ты уже изучишь команды и разберёшься, что VS Code делает за кулисами.

README

Для портфолио желательно указать:

что это за проект;
откуда макет;
используемые технологии;
реализованные возможности;
адаптивность;
accessibility;
ссылка на live demo;
ссылка на GitHub.

🎯 И конкретно для твоего Nexcent

Тебе не нужно проходить весь этот алгоритм за один присест.

Мы можем использовать его как чек-лист проекта:

Сейчас:

→ анализируешь Figma

→ декомпозируешь страницу

→ готовишь папку/файлы

→ начинаешь HTML

Потом последовательно двигаешься дальше.

Каждый завершённый шаг записывается в `docs/01-development.md`.

И самое главное для твоей текущей цели: основной код ты пишешь сам. Если забыл, как сделать что-то в CSS/HTML — сначала пытаешься вспомнить и решить, а уже потом спрашиваешь меня. Так этот проект действительно покажет, что именно ты восстановил после курса, а что ещё требует повторения.
